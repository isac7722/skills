# dev-flow

개인 YAML 프로필로 조사·설계·구현·검증 담당을 배정한다. 사용자는 총괄과 대화한다. 기본 `guided`는 **단계마다 확인**, `yolo`는 **처음 성공 기준과 자동 진행 범위를 확인한 후 PR 초안까지 자동 진행**한다. 첫 버전은 로컬 Orca의 기능 개발과 버그 수정에 사용한다.

## 시작 또는 재개

1. 요청에서 대상 저장소, 목표, 기능/버그, 프로필, 이번 실행의 역할·모델 변경을 식별한다. 저장소의 AGENTS.md와 Git 브랜치·작업 트리를 확인한다. 기존 사용자 변경을 보존한다.
2. [실행 기록과 재개](references/runs.md)를 읽고 먼저 신규/재개를 구분한다. 재개는 실행 ID 또는 목표·저장소로 찾고 여러 개면 사용자에게 선택을 요청한다. 기존 실행의 소유권을 확인하고 저장된 `effective-config.yaml`을 복원한다. 명시적인 설정 변경 요청이 없으면 현재 개인 설정을 다시 합성하거나 생성하지 않는다.
3. 신규 실행만 [설정](references/configuration.md)의 로더로 기본값·프로필·이번 요청을 합성한다. 설정이 없으면 예시를 최초 생성하되 기존 파일은 덮어쓰지 않는다. 고유 실행 ID를 만들고 유효 설정을 고정한다. 신규와 재개 모두 실제 파일·Git·작업자 상태를 대조하고 실행/작업 공간 소유권을 확보한다.
4. 총괄 및 이번 단계의 작업자가 지정된 에이전트인지 확인한다. 현재 에이전트와 지정 총괄이 다르면 `orca-cli`에 따라 총괄을 인계하고 실행 기록 경로를 전달한다. 두 총괄이 같은 실행을 동시에 조율하지 않는다.
5. Orca 작업 전 설치된 `orchestration` 또는 `orca-cli` 스킬을 읽고 해당 실행 파일의 버전별 가이드를 로드한다. [작업자 계약](references/workers.md)을 따른다. 첫 버전은 이미 준비된 로컬 CLI·인증을 사용하며, 실행 불가 시 에이전트를 임의 대체하지 않는다.

## 단계

실행 시작·재개, 사용자 확인 대기·일시 중단·진행 불가, 완료 시 [실행 안내 형식](references/runs.md#채팅에서-실행-안내)에 따라 실행 ID·현재 단계와 상태·기록 링크·재개 명령을 채팅에 표시한다. 저장된 상태를 먼저 갱신하고 그 값을 안내한다.

모든 단계의 결과에는 적용한 스킬, 결과·근거 경로, 미해결 사항, 다음 행동을 포함한다. 진행 권한은 [모드별 확인 규칙](references/modes.md)을 따른다. `guided`는 결과를 저장하고 `awaiting_confirmation`으로 전환한 뒤 사용자 응답을 기다린다. `yolo`도 최초 성공 기준 확인 전에는 구현을 시작하지 않는다. 작업자 완료나 시간 경과는 사용자 확인이 아니다.

### 1. 조사·요구사항

유효 설정의 `roles.research`에 배정한다.

- 기능: 관련 코드·정책을 읽고 `grilling`, `domain-modeling`으로 미정 요구사항과 용어를 정리한다. 외부 근거가 필요한 질문에만 `research`를 적용한다.
- 버그: `diagnosing-bugs`로 실제 증상을 판정하는 재현 루프를 만들고, 최소 재현과 가설 검증의 근거를 수집한다. 진단 스킬의 재현·최소화·가설·계측까지 적용하고, 수정·회귀 테스트는 확인된 구현 단계로 넘긴다. 이 단계에서 제품 수정은 하지 않는다. 재현 스크립트·임시 계측 변경은 따로 기록하고 정리한다. 재현할 수 없으면 원인을 확정하지 말고 필요한 자료를 요청한다.
- 완료 조건: 문제, 범위·제외 범위, 수용 조건, 근거, 미정 결정이 구분되어 있다. 기존 합의로 확인 가능한 사실을 사용자에게 다시 묻지 않는다.

### 2. 설계·작업 계획

유효 설정의 `roles.design`에 배정한다.

- `codebase-design`으로 책임과 공개 인터페이스를 정리한다. 설계 질문에 실제 실험이 필요할 때만 `prototype`을 적용하고, 실험 코드는 구현과 구분한다. 실험 결론은 계획에 반영하고 제품 코드 반영은 구현 단계 확인 후 수행한다.
- 수용 조건별 테스트 경계를 제안하고 각 경계가 잡는 문제와 놓치는 문제를 설명한다. 이 단계의 사용자 확인으로 TDD 테스트 경계도 합의한다.
- 작업을 관찰 가능한 사용자 동작 단위로 나누고 선행 작업, 담당 역할, 수정 범위, 검증 방법을 기록한다. 작은 변경은 하나의 구현 작업으로 충분하다.
- 완료 조건: 구현자가 추측 없이 시작할 명세·작업 그래프·테스트 경계와 worktree/브랜치 계획이 있다. 제품 정책·큰 설계의 미정 사항이 해결되어 있다. 다음 단계 전이는 모드별 확인 절차를 따른다.

### 3. 구현

- 확인된 계획만 `implementation` 역할에 배정한다. 각 작업자는 설치된 `tdd`를 직접 읽고 합의된 공개 경계에서 테스트 실패 확인 → 최소 구현을 한 동작씩 수행한다. 실제 스킬 버전의 절차를 따르고 실패·통과 증거를 남긴다.
- 독립 작업만 병렬로 배정한다. 같은 파일을 수정하거나 선행 결과가 필요한 작업은 순차 진행한다. 작업자와 통합 책임은 [작업자 계약](references/workers.md)을 따른다.
- 합의 범위 안의 컴파일·테스트 오류는 단계 안에서 수정한다. 범위·설계 변경, 실행·인증 불가, 같은 원인으로 세 번 연속 실패하며 진전이 없는 경우 사용자에게 보고하고 멈춘다.
- 완료 조건: 수용 조건별 구현 상태, 변경 파일, 구현자 검증 증거, 미해결 사항이 있다. `guided`는 이 결과를 보고 사용자가 독립 검증 진행을 결정한다. 승인된 `yolo`는 독립 검증으로 자동 전환한다.

### 4. 검증·리뷰

- 새로운 컨텍스트의 `verification` 작업자를 사용한다. 구현자의 결론을 정답으로 주지 않고 명세·기준 SHA·검증 대상 SHA·프로젝트 규칙과 증거를 전달한다.
- 구현 결과를 로컬 커밋으로 고정하고, 프로젝트에서 요구하는 검증을 실행한다. 실행 불가는 통과와 구분한다. 같은 SHA·환경의 유효한 실행 증거는 재사용할 수 있으나 누락·모순·통합 변경이 있으면 재실행한다.
- `code-review`를 적용해 Standards와 Spec을 분리한다. 스킬이 요구하는 독립 리뷰 하위 작업도 지정 검증 에이전트 계열로 수행한다. 규칙 위반과 설계상 제안을 구분한다. diff는 움직이는 HEAD 대신 기록된 `base_sha...target_sha`를 사용한다.
- 지적이 있으면 타당성을 코드·명세와 대조하고 수정 계획을 제시한다. `guided`는 **독립 검증 이후 수정 착수와 수정 결과에 사용자 확인을 받는다.** 승인된 `yolo`는 성공 기준 안의 수정과 새 SHA 검증을 자동 반복한다. 범위·성공 기준·테스트 경계 변경은 두 모드 모두 다시 확인한다.
- 완료 조건: 검증 대상 SHA, 수용 조건별 판정, 두 리뷰 축의 결과, 남은 위험이 있다. 해결되지 않은 요구사항이나 검증 불가를 완료로 포장하지 않는다.

## 전달

검증 결과를 제시할 때 다음 행동을 명시한다: 로컬 완료 또는 커밋 정리·푸시·PR 초안 게시. `guided`는 사용자가 그 행동을 확인하면 실행한다. `yolo`는 최초 승인에 포함된 대상 저장소·base·전달 범위와 성공 기준 충족을 확인한 뒤 추가 질문 없이 실행한다. `pr` 스킬로 변화와 전후 실행 증거·영향을 설명한다. PR은 초안으로 유지하고 병합·배포는 별도 요청에 따른다. 로컬 완료도 허용한다.

로컬 체크포인트 커밋은 재현 가능한 검증을 위한 내부 작업이다. 이번 실행의 확인된 변경만 포함하고, 시작 전에 존재하던 index/worktree 변경을 섞지 않는다. 안전하게 분리할 수 없으면 임의 reset/stash 대신 별도 공간 또는 내용 스냅샷을 사용한다. 커밋 뒤 실제 tree와 검증 대상의 일치를 확인한다. 커밋 금지 지시가 있다면 변경 파일 스냅샷을 고정하고, 커밋 diff를 요구하는 리뷰 스킬의 제약을 설명해 대안을 합의한다. 외부 게시 권한으로 해석하지 않는다.

완료 시 실행 상태와 산출물 링크를 기록한다. 실행 기록과 worktree는 자동 삭제하지 않는다. 정리는 사용자 요청으로 수행한다.
