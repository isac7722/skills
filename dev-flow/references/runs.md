# 실행 기록과 재개

기록은 `~/.agents/dev-flow/runs/<고유 실행ID>/`에 저장한다. 실행ID는 날짜와 무작위 식별자를 조합한다. 사용자 데이터·인증 정보가 있는 원본 로그 전체 대신 필요한 증거만 비밀값을 가려 기록한다.

## 채팅에서 실행 안내

실행 시작·재개, 사용자 확인 대기(`awaiting_confirmation`), 일시 중단(`paused`), 진행 불가(`blocked`), 완료(`completed`) 시 다음 정보를 짧게 표시한다. 메시지는 먼저 저장한 실제 state.yaml을 기준으로 작성하고 예시 ID를 그대로 사용하지 않는다.

```text
실행 ID: <run_id>
현재 단계: <단계 이름> / <status> · <guided 또는 yolo>
기록: <state.yaml의 절대 경로 링크>
재개: /dev-flow <run_id> 이어서 진행해줘.
```

안내하는 ID는 dev-flow의 run_id다. Orca run/task/dispatch ID는 작업자 추적용이며 재개 명령에 대신 넣지 않는다. 같은 채팅의 단계별 확인에서는 ID를 다시 입력할 필요 없이 현재 제시된 행동에 답하면 된다. ID를 모르면 목표·저장소로 실행을 찾고, 후보가 여러 개일 때 ID·목표·저장소·단계·상태를 보여주고 선택받는다.

완료 안내에도 같은 명령을 제공하되 “완료된 실행: 재개 명령은 기록 확인용”이라고 덧붙인다. completed 실행을 조회했다고 구현·게시를 다시 실행하지 않는다. 추가 작업은 사용자 요청을 받아 기존 기록을 참조하는 새 실행으로 만든다. 실행 기록 생성 전에 실패했다면 ID를 만들어 보여주지 않고 “실행 미생성”과 실패 원인을 알린다.

## 파일 책임

- `state.yaml`: 상태와 경로, 작업자 식별자. 총괄만 쓴다.
- `effective-config.yaml`: 실행에 적용된 설정.
- `requirements.md`, `plan.md`: 단계별 명세와 작업 계획. 프로젝트 기준 문서는 경로로 참조한다.
- `results/<단계>-<회차>.md`: 작업자 결과와 증거 위치.
- `decisions.md`: 사용자 판단의 대상, 실제 응답과 허용한 다음 행동. 최신 판단으로 이전 기록을 덮어쓰지 않는다.

명세는 로컬 파일 기반으로 관리한다. mattpocock 스킬에 tracker가 필요하면 이 실행의 명세·작업 목록 경로와 상태 변경 방식을 명시한다. 외부 이슈 트래커 설정을 추측하지 않는다.

## state.yaml 필수 정보

```yaml
version: 1
run_id: "20261117-example"
goal: "기록 저장과 조회"
kind: feature
mode: guided
yolo_authorization: null
repo_path: "/absolute/repo"
worktree_path: "/absolute/worktree"
branch: "feat/example"
base_sha: "실제 기준 SHA"
target_sha: null
stage: research
status: running
revision: 1
coordinator: {agent: codex, handle: "실제 Orca handle"}
workers: []
pending_confirmation: null
delivery: draft-pr
```

stage는 `research`, `design`, `implementation`, `verification`, `delivery`다. status는 `running`, `awaiting_confirmation`, `blocked`, `paused`, `completed`다. kind는 `feature`, `bug`다. workers에는 task/dispatch ID, 에이전트, 작업 위치, 입력 리비전, 결과 경로, 상태를 기록한다.

guided 또는 yolo 최초·변경 확인이 필요한 결과를 확정할 때 입력 명세·계획과 결과 파일의 SHA-256, 대상 Git SHA, 사용자에게 제시한 다음 행동을 pending_confirmation에 기록한다. 사용자의 명시적 응답을 decisions에 저장하고 대상이 일치할 때만 상태를 바꾼다. guided의 “진행해”는 현재 제시한 한 단계 전환에 적용한다. yolo는 [최초 승인 계약](modes.md)을 별도로 저장하며 그 계약에 명시된 후속 단계에만 권한을 적용한다. 침묵·시간 경과·일괄 추천 동의를 이후 모든 단계의 확인으로 확장하지 않는다. 유효한 yolo 승인 범위의 자동 전이는 pending_confirmation을 새로 만들지 않고 승인 계약 ID·결과 회차·다음 행동을 기록한다.

`revision`은 명세·계획 입력이 바뀔 때 증가한다. 같은 명세의 수정 반복은 결과 회차와 target SHA로 구분한다. 실행·인증 불가 또는 같은 원인으로 세 번 연속 진전 없이 실패하면 원인과 재개 조건을 기록하고 `blocked`로 전환한다.

확인 요청 시 작업 트리 기준선도 저장한다: HEAD, 시작 전 사용자 변경 목록, index diff 해시, worktree diff 해시, 관련 untracked 파일의 경로·내용 해시. 결과에 영향을 주는 ignored 설정도 비밀값 원문 대신 해시로 식별한다. 바이너리·삭제·파일 모드 변경이 포함되도록 Git diff를 캡처한다. 사용자 응답 직후와 검증 직전에 기준선을 재계산한다. guided에서 확인 대기 중 입력 명세·결과·코드·다음 행동이 달라졌으면 영향받는 확인을 새로 받는다. yolo의 승인 범위 내 구현·수정·검증에 따른 코드와 결과 변경은 정상 진행이며 그 자체로 재확인하지 않는다. 두 모드 모두 설명되지 않는 외부 변경이나 승인 계약 변경은 영향 분석 후 다시 판단받는다. 무관한 변경은 영향이 없다는 근거를 기록한다.

파일은 임시 파일에 쓴 뒤 원자적으로 교체한다. 총괄 하나만 상태를 쓰며, 인계 시 이전 총괄이 진행을 종료한 것을 확인한 후 소유권을 바꾼다. 실행과 작업 공간을 획득할 때 `~/.agents/dev-flow/locks/` 아래에 각 실행 ID 및 실제 worktree 경로 해시로 이름을 만든 잠금 디렉터리를 원자적 mkdir로 생성한다. 이미 존재하면 소유 실행·총괄·활성 dispatch를 조회한다. 동일 실행과 동일 총괄의 정상 재개임을 확인하면 기존 잠금을 재사용한다. 다른 소유자 또는 소유권 불명확 시 덮어쓰지 않고 `blocked`로 처리한다. 두 잠금을 순차 획득하다 실패하면 이번 시도에서 새로 획득한 잠금만 반환한다. 잠금에는 소유 정보와 획득 시각을 기록한다. 총괄만 상태를 쓰고 지정 worker만 해당 배정의 파일을 쓸 수 있다. 오래된 시각만으로 잠금을 제거하지 않는다. 확인 대기 중에도 worktree 잠금은 유지하고 완료/인계 시 활성 쓰기 작업이 종료됐음을 확인한 뒤 소유 총괄이 해제한다. 소유권이 불명확하면 병렬 조율을 시작하지 않는다. worker는 실행 기록 중 자신의 결과 파일만 쓴다. 구현 코드 수정은 배정된 작업 범위에 따른다.

## 재개 절차

1. 현재 개인 설정과 무관하게 저장된 유효 설정을 복원한다. 저장된 설정이 없거나 손상됐으면 현재 설정으로 대체하지 않고 복구 판단을 요청한다. 저장된 저장소·worktree·브랜치가 실제 존재하는지 확인한다. HEAD, tracked/untracked 변경, 명세·결과 해시를 대조한다. 커밋 SHA가 같아도 파일 변경이 있으면 같은 검증 대상으로 간주하지 않는다.
2. 저장된 task/dispatch를 설치된 Orca의 조회 기능으로 확인한다. 상태 조회 실패나 조용한 터미널은 작업 종료의 증거가 아니다. 살아 있는 작업을 중복 시작하지 않는다.
3. 대기 중 사용자 판단이 있으면 같은 결과와 다음 행동을 제시한다. 확인 대기 당시 입력·결과·코드·다음 행동이 달라졌으면 관련 확인을 무효화하고 새 리비전으로 다시 판단받는다. 이미 승인된 yolo 재개는 저장된 승인 계약과 정상 작업 이력을 대조하며, 유효하면 추가 확인 없이 계속한다. 설정 파일의 mode 변경은 진행 중 실행에 자동 적용하지 않는다.
4. 늦게 도착한 결과는 dispatch와 입력 리비전을 대조한다. 이전 계획의 결과를 현재 완료로 적용하지 않는다. 새 리비전의 쓰기 작업을 배정하기 전, 이전 쓰기 작업의 실제 종료를 확인하거나 별도 worktree로 격리한다. 메시지 배제만으로 이전 worker의 파일 쓰기가 중단되었다고 가정하지 않는다.
5. 사용자가 중단을 요청하면 `paused`를 기록하고 Orca 중단 지침으로 활성 작업자를 처리한다. 재개 시 실제 중단 여부를 확인한다.

작업자에게 직접 내린 지시가 범위·수용 조건·설계를 바꾸면 변경 제안으로 총괄에 보고한다. 총괄은 영향받는 단계로 돌아가 새 리비전과 확인을 기록한다. 기존 범위의 문구·구현 수정은 결과에 기록한다.

완료 판정은 명세 충족, 필요한 검증의 결과, 미해결 사항의 사용자 판단과 전달 결과를 근거로 한다. PR 게시 실패는 delivery의 blocked 상태이며 구현을 다시 시작할 이유가 아니다. 기록과 작업 공간은 자동 삭제하지 않는다.
