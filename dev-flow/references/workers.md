# 작업자 배정과 작업 공간

## Orca 사용

총괄은 설치된 `orchestration` 가이드를 읽고 그 버전의 worker 실행·메시지·복구 절차를 따른다. CLI와 옵션을 이 문서의 오래된 예시에서 추측하지 않는다. Codex↔Claude 교차 배정은 Orca worker를 사용하며 현재 모델의 내부 서브에이전트로 대체하지 않는다.

worker를 시작한 뒤 버전별 가이드가 요구하면 턴을 끝내고 Orca의 완료/질문 알림으로 재개한다. 진행 상황을 무한 polling하거나 별도 스크립트로 inbox를 소비하지 않는다. 질문은 총괄이 합의 자료로 답하고, 사용자 결정이 필요한 것만 전달한다. 작업자 완료는 사용자 확인과 별개다. 총괄은 실행 모드의 기존 권한을 확인한 후에만 다음 단계를 배정한다.

새 프로세스를 시작하기 전에 이번 단계의 스킬 경로와 에이전트 실행 가능 여부를 확인한다. 실행 실패나 불확실한 응답은 dispatch/receipt를 조회하고 설치된 복구 지침을 따른다. 동일 시작 명령을 무작정 재실행하지 않는다.

## worktree

사용자가 별도 worktree를 요청했으면 Orca로 생성한다. 이미 지정된 기능 worktree가 있으면 재사용한다. 기준 ref를 실제 SHA로 기록하고 작업자마다 절대 경로와 브랜치를 확인시킨다. 수정은 지정 작업 공간에서 수행한다.

기본은 기능 worktree 하나에서 단계별 순차 실행이다. 구현자가 쓰는 동안 최종 검증자가 같은 파일을 검사하지 않는다. 병렬 구현이 필요한 경우만 작업자별 worktree를 만들고, 선행 변경이 포함된 통합 브랜치의 SHA에서 시작한다. Orca의 부모/자식 표시가 Git 기반 커밋을 결정한다고 가정하지 않는다.

통합은 총괄이 한 번에 하나씩 수행한다. 충돌 해결을 구현 역할에 맡기고 통합 후 영향을 받는 검증을 수행한다. 다른 실행이 같은 worktree를 사용 중이면 새 공간을 배정하거나 해당 실행 종료를 기다린다. 실행 포트·개발 DB·프로젝트 빌드 잠금은 worktree만으로 격리되지 않으므로 프로젝트 규칙에 따라 분리한다.

## 역할 적용

조사·설계도 각각 유효 설정의 research·design 역할로 실행한다. 총괄은 역할의 agent와 명시된 model·effort가 현재 세션과 일치함을 확인할 수 있을 때만 직접 수행할 수 있다. 일치 여부가 불명확하거나 다르면 해당 설정의 Orca worker를 실행한다. 검증은 일치하더라도 항상 새 컨텍스트를 사용한다.

하위 조사 작업은 research, 설계 실험은 design, 구현은 implementation, 리뷰는 verification 설정을 따른다. 모델·추론 강도는 명시된 값만 전달하고 실제 launch receipt와 비교해 기록한다. 런타임이 다르게 적용하거나 지원하지 않으면 조용히 계속하지 말고 알린다.

## 작업 지시 템플릿

각 지시는 다음 내용을 포함하고 전체 대화 복사보다 파일 경로를 우선한다.

```text
실행 ID / 단계 / 입력 리비전 / 모드 / 유효한 승인 계약 경로:
역할 / 지정 에이전트 / 명시된 경우 모델·추론 강도:
목표와 담당 범위:
작업 공간 절대 경로 / 브랜치 / 기준 SHA:
명세·계획·AGENTS.md 경로:
직접 읽어 적용할 SKILL.md 경로와 버전:
수정 가능한 범위 / 선행 조건:
검증 명령과 성공·실패의 의미:
결과 파일 경로:
완료 조건과 미해결 사항 보고 방식:
```

worker는 시작할 때 실제 경로·브랜치·필수 스킬 접근을 확인하고, 불일치하면 보고한다. 범위를 바꾸는 직접 지시는 총괄에 제안하고 확인 전 확장 구현을 시작하지 않는다. 결과 파일에는 수정 파일, 커밋 또는 변경 상태, 수용 조건별 결과, 실행 명령·exit code·핵심 출력, 미해결 사항을 쓴다. 비밀값은 제거한다.

worker는 주입받은 task/dispatch ID로 성공 또는 실패를 보고한다. 총괄은 해당 입력 리비전의 증거를 확인한 후 단계 결과를 만든다. 실패 보고를 완료로 바꾸거나 timeout만으로 작업자가 종료되었다고 판단하지 않는다.

## 단계별 스킬 연결

| 역할 | 조건에 따라 적용할 mattpocock 스킬 |
|---|---|
| 조사 | grilling, domain-modeling, research; 버그는 diagnosing-bugs |
| 설계 | codebase-design, domain-modeling; 실험이 필요하면 prototype |
| 구현 | tdd |
| 검증 | code-review |
| 전달 | pr |

하위 스킬의 사용자 확인 요구는 이미 합의한 내용으로 충족되는지 먼저 판단한다. 예: 설계 단계에서 확인한 테스트 경계는 다시 묻지 않는다. 새 경계·새 정책은 다음 판단 대상으로 제시한다. 테스트 실패 같은 통상적 구현 반복과 독립 검증 뒤의 수정 착수를 구분한다. guided에서는 후자에 별도 확인이 필요하고, yolo에서는 최초 승인 범위 안의 수정·재검증을 계속한다. 하위 스킬에도 이미 합의한 범위와 테스트 경계, 유효한 yolo 승인 경로를 전달해 같은 내용을 반복해서 묻지 않게 한다.
